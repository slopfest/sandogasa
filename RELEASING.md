# Releasing sandogasa

The maintainer's procedure for cutting a release, moved here from the
agent instructions (`.claude/CLAUDE.md`, also `AGENTS.md`) so they stay
short for everyday work. Read it in full before starting a release: the
sections are in the order they apply.

## Before the release: sweeps and checks

- **Sweep the GitHub issue tracker before cutting a release, and again when planning the next stretch of work.** `gh issue list --state open`, then check each against the code, not against memory: an issue is often fixed in passing by work that never mentioned it (#3 was closed by a check written three months earlier; #11 by a rewrite that retired the flow it described). Close the stale ones with the fixing commit's hash and subject and the first release tag that shipped it — `git log --diff-filter=A -- <file>` or `git log -S<term>` finds the commit, `git tag --contains <sha> -l 'v*' | sort -V | head -1` the tag; if the commit cannot be pinned down, the release alone is fine. Give each that remains a milestone (`Next patch`, `Next minor` or `1.0`, below), or, when it isn't planned for a release, one of three labels saying why: `blocked` (waiting on something outside this repository, which the issue names; not for an issue that only waits on another issue here), `exploratory` (too large or undecided to plan yet) or `priority::low` (nothing waits on it). The sweep checks against the code only the issues with a milestone, and those with no milestone and none of the three labels (`gh issue list --state open --search 'no:milestone -label:blocked -label:exploratory -label:priority::low'`), so the parked ones are not read again each time; check a `blocked` one again when its blocker may have cleared. Corollary that makes the sweep cheap: **when a commit implements or obsoletes a tracked issue that its own `Fixes #N` or `Resolves #N` does not close, close the issue in the same sitting**, with the same commit-and-release pointer, rather than leaving it for the sweep to find
- **Sweep the code scanning alerts before cutting a release too.** `gh api '/repos/michel-slm/sandogasa/code-scanning/alerts?state=open&per_page=100' --paginate`, grouped by rule and path. The point is not to reach zero — it is to find the few that are not false, and they do not announce themselves: on 2026-10-13, 22 `rust/cleartext-transmission` findings looked like one class, and **7 of them were real** (`sandogasa-distgit`, `-jira` and `-nvd` attached an API token to a base URL of any scheme, while six sibling crates already called `ensure_secure_url`). Had a single blanket "guarded by ensure_secure_url" dismissal been written over all 22, the real ones would have been buried by their own explanation. So **check each group against the code before dismissing it**, and prefer fixing to dismissing: a rename of a parameter called `secret` that held `"API key"` cleared 6 alerts honestly. Dismiss with `-f dismissed_reason="false positive"` (the API's enum has spaces, not underscores) and a `dismissed_comment` **under ~280 characters** — a longer one is rejected — naming the guard so the next reader can check the claim instead of trusting it. An already-dismissed alert's comment cannot be edited; reopen it first. Where a rule can never be right here, exclude it in `.github/codeql/codeql-config.yml` with the reason in the file rather than re-triaging it every release; note that CodeQL has no alert-suppression comment for Rust, so there is no per-line escape hatch, and that **GitHub's default setup ignores that config file** — the analysis runs from `.github/workflows/codeql.yml` so the exclusions are read
- **Check `docs/tokens.md` against the services at each minor release.** The page and every `config` prompt come from `sandogasa_config::credentials`, and tests keep them in step with each other and with the tools that keep each secret, but nothing checks the scopes against the services themselves: a forge renames a scope, or a tool starts writing where it only read. Confirm each tool's row against what its code calls, and any scope that changed against the service's token page, and fix the table, not the page (`make tokens` regenerates it)
- **Check the upstream primer's Tools part when a release adds, renames or removes a tool or a subcommand, and at each minor release anyway.** `parts/05-tools.md` in [slopfest/upstream-primer](https://github.com/slopfest/upstream-primer) (local clone `~/src/github/slopfest/upstream-primer`) points fleet teams at sandogasa's tools by name, subcommand and README link. The primer has no other link to this repository, so a renamed subcommand leaves it wrong without anyone noticing. `git diff --stat <previous tag> -- tools/*/man/` shows which tools' commands changed, since each man page lists its subcommands. Check only that the names, subcommands and links still hold. Changes go to that repository, for Michel to review, not into this release.

## Running the gates

- **Check free disk before starting, and budget tens of gigabytes.** The gates are what fill `target/`, not day-to-day work: `cargo clippy --workspace --all-targets` and `cargo test --workspace` build every test binary and dev-dependency for ~41 crates, `cargo cov` writes a separately instrumented copy of the whole workspace, and `cargo semver-checks` builds rustdoc for the current *and* baseline version of every library crate. On 2026-08-26 that took a 237G disk to under 1G free, and the low-disk warning was noticed by luck while `cargo ws publish` was already in flight — running out mid-publish would have left the workspace half-published. Run `df -h .` first; if the margin is thin, clear space *before* the gates rather than during them
- **`make sweep` will not save you from this** — it deliberately keeps `target/debug` (see the comment in `scripts/sweep.sh`), which is the tree the gates inflate, and it only becomes useful *after* publishing, when the semver-checks baseline it clears has been invalidated. When `target/debug` itself has to go, `cargo clean --workspace` is the tool: it removes the workspace's own crates, which are nearly all of it, keeps the compiled dependencies so the rebuild is short, and reports what it removed (`-n` shows it first); plain `cargo clean` drops the dependencies too. The script's "1.3GB" figure describes a plain dev build, not the state after a full gate run
- **Start the slow gates in the background, not by letting them time out into it.** `cargo semver-checks --workspace` takes well over 10 minutes on this workspace (it builds rustdoc for both the current and the baseline version of every library crate); coverage and a full `cargo test --workspace` are minutes each. A foreground call that exceeds its timeout is moved to the background, but everything it printed *before* the move is lost, so a run that was 90% done reports on its last two crates. Launch those with `run_in_background` from the start
- **Running the release gates: never pipe a gate whose verdict is its exit status.** `cargo semver-checks`, `cargo audit`, `cargo test`, `scripts/check-published.sh` and friends answer with an exit code, and `cmd | tail` reports the *pipe's* status — so a failing gate reads as a pass. Redirect to a log and record the status explicitly (`cargo semver-checks --workspace > /tmp/semver.log 2>&1; echo "EXIT=$?"`), then grep the log. Piping is fine only when the status is also captured (`${PIPESTATUS[0]}`)
- **Do not mutate `Cargo.toml` while a background gate is running.** Bumping the version under a running `cargo semver-checks` invalidates it — the baseline it is resolving disappears (`package ID specification sandogasa-x@<old> did not match any packages`) and the whole run has to be repeated. Order: audit and semver-checks first, *then* bump, then man pages, then the test/clippy/fmt/coverage gates

## Advisories and dependency ranges

- **A "patched" version may only deprecate the vulnerable API.** RUSTSEC-2026-0386 (unsound `AsyncFd` constructors) is "fixed" in tokio 1.54.1 by deprecating them; they still exist, and Fedora's update for it was deliberately left with type "unspecified", not "security". So for every advisory `cargo audit` reports, warnings included, read the advisory and the fixed release's changelog for the mitigation, not just the version, and confirm nothing we ship calls the affected API:
  - our code: `make check-deprecated` (part of `make release-checks`) fails on any `use of deprecated` with every feature on, and on any `#[allow(deprecated)]`; `make clippy` covers default features only
  - dependencies: `make find-api-use PATTERN='<regex>'` searches every locked crate's source, since lints are capped for dependency code and a dependency calling the API never warns. Matches in the advisory crate's own tests and changelog are expected; anything else needs a look

  Record the outcome in the release commit
- Before tagging, if any workspace dependency uses a version range, re-test both the floor and the ceiling (see "Security advisories whose fix isn't packaged in Fedora yet" below)
- Before a semver-breaking release, check for deps that themselves require a major version bump and consider bundling those upgrades with your own breaking release. Use `cargo update --dry-run --verbose` and look for `Unchanged <crate> (available: <new major>)` lines — do NOT use `cargo outdated`, which doesn't understand `[workspace.dependencies]` inheritance and falsely reports "All dependencies are up to date" for this workspace

- **Security advisories whose fix isn't packaged in Fedora yet** — decide by actual exposure, not the paper severity:
  - **Real exposure** (we parse/receive attacker-controllable input on the affected path): bump the requirement to the fixed version immediately and flag the missing Fedora package in TODO.md as a prerequisite for Fedora packaging work.
  - **Not exploitable for us** (e.g. DoS-only on data from trusted TLS endpoints, or the vulnerable API isn't the one we use): prefer a **version range** spanning Fedora's version up to the fixed series, e.g. `quick-xml = ">=0.40, <0.42"`. Cargo's resolver pins the max (the fixed version) in `Cargo.lock`, so our builds, `cargo install` users, and `cargo audit` all see the fixed version with no ignore entries — while Fedora builds still resolve against the version it has. **Requirements:** verify the floor actually works (`cargo update -p <crate> --precise <floor>` then build + test the affected crates, then restore), and record in TODO.md to tighten the floor once Fedora catches up. While any range is in effect, **every release must re-test both ends** — `cargo update -p <crate> --precise <floor>`, build + test the affected crates, restore to the ceiling, test again — since either end can drift (a new patch release at the ceiling, code changes that silently break the floor). Ranges are meant to be **short-lived**: tighten back to a single requirement as soon as Fedora ships the fixed version on all relevant branches. Fall back to an `audit.toml` ignore with a written rationale only when a range is impossible (API breakage across the range)

## Versions, CHANGELOG, milestones and man pages

- Before bumping versions, run `cargo semver-checks` on each library crate — the crates under `crates/`, which is exactly what `make semver-checks` covers — to determine the correct version bump. **A tool crate's library target is not semver surface.** Several tools under `tools/` have a `src/lib.rs` so the binary and its tests can share code; that library is internal to the tool, carries no stability promise, is not run through semver-checks, and changes to it never drive the bump or earn a `(breaking)` heading. Only the standalone library crates do (v0.24.0's minor bump rested on `sandogasa-forgejo` and `sandogasa-gitlab`, not on the tool it also listed). Pre-1.0: patch bump is fine for anything non-breaking (including new tools, new crates, and new public items); bump the minor (e.g. 0.10.x → 0.11.0) only for actual breaking changes. Post-1.0: follow strict semver — new public surface (new crates, new tools, new modules, new items) requires at least a minor bump; breaking changes require a major bump
- **A minor bump is the time to do 1.0 work.** When a pre-1.0 release needs a minor bump anyway (`cargo semver-checks` reports a break, or a breaking change was planned), take issues or items from the `1.0` milestone (#216) into the same release: `#[non_exhaustive]` on enums and caller-built structs, options structs instead of positional parameters, typed errors. Each goes under the release's `(breaking)` CHANGELOG headings, instead of costing another minor bump later, or a major one after 1.0. Look at the milestone as soon as a break is known, not at tagging time, so there is room to do the work. See DEVELOPMENT.md, "Extensible APIs before 1.0"
- Before tagging a release, review the `Unreleased` section in CHANGELOG.md, rename it to the version, and update any README.md files affected by the changes (root, tool, or library crate)
- **Regenerate the man pages after bumping the version, not before** — each page's `.TH` line carries `sandogasa <version>` (the footer, as `man bash` shows "GNU Bash 5.3"), so the pages must be rewritten once the new version is in `Cargo.toml`. The `man_page_matches_cli` tests fail while a page still names the old version, so a forgotten regeneration is a test failure rather than a stale footer shipped to users. Order at release time: bump versions → `make man` → run the test suite → commit → tag
- **Milestones say which release an issue is planned for.** Three open milestones roll forward: `Next patch`, `Next minor` and `1.0` (the API work in #216). Give a new issue one when it is filed, if it is planned for a release at all; leave it off otherwise. An issue has at most one. At release time, rename the milestone the release cuts to its version (`v0.29.1`), open a fresh one with the old name, move the issues still open in the renamed one into it, and close the renamed one, so it lists only what the release shipped; when a release planned as a patch turns out to need a minor bump, move `Next patch`'s issues into `Next minor` first. Closed milestones then record what each release shipped

## Scratch build

- **Scratch-build the release on every Fedora architecture before publishing to crates.io**, as packaging-lore's `fedora.md` asks for projects packaged in Fedora. v0.29.0's tests failed in s390x `%check` after the crates were published and the tag pushed (fixed in 70eb7154, backported to every branch). Here: write the tarball into the dist-git checkout (`~/src/fedora/pkgs-sig-rust/sandogasa/`) with `git archive --prefix=sandogasa-<version>/ -o sandogasa-<version>.tar.gz HEAD`, after the release commit (version bump, `make man`) and before `cargo ws publish`, since a fix found then still goes into the same version

## Publishing to crates.io

- Before tagging, publish all crates to crates.io with `cargo ws publish --publish-as-is --publish-interval 30 --no-remove-dev-deps --no-git-commit --allow-dirty` (from [cargo-workspaces](https://github.com/pksunkara/cargo-workspaces); install via `cargo install cargo-workspaces`). `--publish-as-is` uses existing `Cargo.toml` versions (no bump, no prompt); it automatically skips crates already on crates.io at that version, so re-running after a partial failure is safe. `--publish-interval 30` throttles to stay under crates.io rate limits; `--no-git-commit` skips the version-bump commit cargo-workspaces would otherwise make; `--allow-dirty` tolerates uncommitted `Cargo.lock` edits. **`--no-remove-dev-deps` is not optional here.** Without it cargo-workspaces deletes a crate's entire `[dev-dependencies]` table whenever any entry refers to a workspace member with a version (`warn removing dev-deps since some refer to workspace members with versions`), which is every crate under `tools/` — they all dev-depend on `sandogasa-cli` for the `man_page_matches_cli` test. Four releases shipped that way before anyone noticed, because our tests live in `#[cfg(test)] mod tests` inside `src/` and therefore ship in the tarball: debcargo runs `cargo test` at build time for a crate that looks dependency-free, so the first Debian build of dbranch ran them and died on a missing `tempfile`. `scripts/check-published.sh` now fails the release if a published crate lost the dev-dependencies its source declares. Raw `cargo publish --workspace` also works for the initial attempt but fails hard on the first already-published crate, so don't use it for retries
  - **Picking `--publish-interval` (compute it; the workspace is past the burst).** crates.io's defaults: new *versions* of existing crates get a burst of **30** refilling **1/min**; brand-new crate *names* get a burst of **5** refilling **1 per 10 min** (source: crates.io `rate_limiter.rs`). The binding constraint is the version-bump burst of 30. The bucket refills to full after ~30 min idle, so on a normal release it starts at 30. If the number of crates getting a version bump (`N`) is ≤ 30, the interval can be near zero; once `N` exceeds 30 you need roughly `interval ≥ 60 × (N − 30) / N` seconds so the tail doesn't 429. A 429 is **not fatal** — re-run the same command and `--publish-as-is` skips the already-published crates, waiting out the ~1/min refill.
    - The workspace now bumps **every** crate on a release (they share `version.workspace = true`), so `N` is the full member count and is **well past 30** — the interval can no longer be driven to zero no matter how idle the bucket is, and there is a hard floor of about `N − 30` minutes on the run regardless of what you pass. Compute the interval each time rather than reusing a number: `N` grows with every new crate.
    - Worked examples: **v0.15.2** — ~36 crates, ~34 version bumps + 2 new → floor ≈ 60×4/34 ≈ 7s, used `10` (~6 min). **v0.19.1** — 41 crates all bumping → floor ≈ 60×11/41 ≈ 16s, used `20` (~14 min), no 429s. The `30` in the command above is a conservative fallback, not the right answer for a workspace this size (~21 min for 41 crates)
- **After publishing, verify every crate actually landed — before tagging.** Run `make check-published` (`scripts/check-published.sh`, optionally with a version argument). `cargo ws publish` can stop partway on a 429, an interrupted upload, or a crate whose packaging fails, and a tag pointing at a half-published workspace is worse than a tag that arrives late. The script lists what is missing and prints the re-run command; `--publish-as-is` skips whatever already landed. Note that **crates.io requires a User-Agent** under its [API data access policy](https://crates.io/data-access) and answers `200` with an error body when one is absent — so an ad-hoc `curl` check without a UA reports every crate as missing, which looks exactly like a failed publish. Use the script rather than hand-rolling the query
- **Publishing rewrites `Cargo.lock`** — packaging each crate resolves it without the workspace's dev-dependencies, and `--allow-dirty` lets that be written back, so `git status` afterwards shows a lockfile with entries like `tempfile` and `wiremock` removed. Discard it (`git checkout Cargo.lock`) and confirm a plain `cargo build --workspace` leaves the tree clean; do not commit the stripped version

## Tagging

- Always use `git tag -s` (GPG sign) when tagging
- Before tagging, verify there are no uncommitted changes (`git status` must be clean)
- Write the tag message as a scannable plain-text bullet-point summary, not as a copy of the CHANGELOG entry — GitHub renders the tag message on the release page and long prose paragraphs read poorly there. GitHub does NOT render Markdown in tag messages, so stick to plain text: no `**bold**`, no `[link](url)` syntax, no `##` headings. Structure:
  1. First line: the tag name alone (e.g. `v0.10.2`) — git's subject/body convention. GitHub renders this as the release title and the rest as the body; without it the first bullet becomes the title
  2. Blank line
  3. One bullet per new tool / library crate / significant feature, using `-` as the marker, wrapped at 72 columns. Breaking and security bullets come first, each saying what broke and how to migrate ("Pass an empty slice for the old behavior"). A new tool or crate leads with its headline ("New foo tool"), an em-dash, then a sentence or two on what it does. Every other bullet is a plain sentence that starts with the tool and says what it now does ("dbranch sets the upstream on the first push of a new branch"), with no em-dash
  4. Blank line, then the documents the release jobs attach and regenerate from the tag, one `-` line each, under `Documents:`: every talk under `talks/` the release adds or changes (`git diff --name-only <previous tag> HEAD -- talks/`), as `<name>.pdf` and its title, every recording under `casts/` it adds or changes (`git diff --name-only --diff-filter=d <previous tag> HEAD -- 'casts/*.cast'`), as `<name>.gif` and what it shows, and always `sandogasa-trajectory-vX.Y.Z.pdf`, the development trajectory report. A reader of the release page then knows what to look for among the assets, and the check after the release (below) has a list to tick off
  5. Blank line, then a plain URL linking back to the anchored CHANGELOG entry at the tag version (e.g. `Full details:\nhttps://github.com/michel-slm/sandogasa/blob/vX.Y.Z/CHANGELOG.md#vxyz`)
- Keep each tag-message bullet to its headline and two or three points; the CHANGELOG link carries the rest. Three habits made earlier release pages hard to read, so avoid them:
  - **Packed bullets:** clauses chained with semicolons, parentheses nested in lists, a whole tool's changes squeezed into one line ("new ping (…), list-issues (…), timeline (…); retire takes…"). Split a tool with two real headlines into two bullets, and drop the minor points
  - **Aphorisms built on "X is not Y":** "an update that fixed nothing is not the fix", "so 'slower' separates from 'built something bigger'". They sound clever, but the reader has to decode them. Say what changed: "a failed Bodhi query is reported, not taken as 'no updates'"
  - **Internal names in a tool's bullet:** function, field and type names (`whatrequires_src`, `InventoryMeta`) belong only in a library or breaking bullet, where a caller needs them
- Pass the message via `git tag -s -F <file>` with a pre-written file so the formatting survives — avoid lines starting with `#` (git strips them as comments unless you add `--cleanup=whitespace`)
- **Signing needs a terminal the GPG agent can prompt on — tags and, with `commit.gpgsign` on, every commit.** `git tag -s` or `git commit` from a non-interactive shell fails with "gpg failed to sign the data" unless the key is already cached (`gpg-connect-agent 'keyinfo --list' /bye` shows a `1` in the cached column). pinentry does reach the human's terminal when one is attached, but the prompt can vanish after a second and the run then fails with "No passphrase given"; nothing partial is written, so check `git log` and the staging state, and retry once when the human says the prompt is back — or hand them the exact `git commit -s -F <file>` / `git tag -s -F <file> <tag>` to run themselves. And gate everything after it on its success: on the v0.24.1 release a chain joined with `;` pushed `main` and created the draft release with the tag still missing. The draft, keyed on the tag name, happened to work once the tag arrived, but a push after a failed tag is not something to rely on

## Pushing, and checking what the release jobs attach

- After publishing and tagging, push with `git push --follow-tags`
- **Pushing the tag starts the prebuilt-binary workflow, which needs a draft GitHub release waiting for it.** `.github/workflows/release.yml` (generated by cargo-dist; see `[workspace.metadata.dist]` in the root `Cargo.toml`) builds dbranch for x86_64 and aarch64 musl and uploads the archives, then undrafts the release. It is configured `create-release = false`, so it uploads into a release that already exists rather than writing its own title and body — which is what keeps the tag-message convention above on the release page. So right after `git push --follow-tags`, create the release as a draft from the same message file: `gh release create <tag> --draft --title <tag> --notes-file <file>`. The build takes minutes and the upload job runs last, so the draft only has to exist before that job reaches it. If it is missing the upload fails; create it and re-run the job
- **Give Actions a few minutes before concluding the tag push did not fire the workflow, and never delete a pushed tag on that suspicion.** On the v0.22.0 release the run was absent from `gh run list` and from `actions/workflows/<id>/runs` (`total_count: 0`) for a good minute after the push, which read as a trigger that had not matched — the tag was deleted and re-pushed to force a fresh event, and the run then appeared, very possibly the one the *first* push had already queued. Registration simply lags. Before touching the tag, confirm the real causes: that the pattern matches (`git ls-tree -r <tag> --name-only | grep .github` proves the workflow exists at the tagged commit), that Actions is enabled (`gh api repos/<o>/<r>/actions/permissions`), and that the workflow is `active`. If all three hold, wait
- **Then check the binaries landed, the way `make check-published` checks the crates.** `gh release view <tag>` should list four assets — `dbranch-x86_64-unknown-linux-musl.tar.xz` and the aarch64 one, each with a `.sha256` — and the release should no longer say Draft. A half-uploaded release is the same failure as a half-published workspace, and it is silent: `cargo binstall dbranch` simply falls back to building from source, so nobody reports it. Smoke-test that command afterwards, since it is the thing the release exists to make work
- **And check the talk PDFs landed.** `.github/workflows/talks.yml` builds each talk under `talks/` that the release adds or changes (since the previous `v*` tag) and attaches `<name>.pdf` to the release, waiting up to 10 minutes for the draft to exist. So `gh release view <tag>` also lists one PDF per such talk (`git diff --name-only <previous tag> <tag> -- talks/` says which), besides dbranch's four assets. A missing one is as silent as a missing binary; re-run the job, or run it by hand with `gh workflow run talks.yml -f tag=<tag>`
- **And check the recordings' GIFs landed.** `.github/workflows/casts.yml` renders each recording under `casts/` that the release adds or changes with agg and attaches `<name>.gif`, waiting for the draft the same way. `gh release view <tag>` lists one GIF per such recording; re-run the job, or `gh workflow run casts.yml -f tag=<tag>`. Run without a tag, it renders every recording into a workflow artifact instead, to check how they look
- **And check the trajectory report landed.** `.github/workflows/trajectory.yml` measures every release tag up to the new one (`scripts/build-trajectory.sh`, see `reports/trajectory/README.md`) and attaches `sandogasa-trajectory-<tag>.pdf`, waiting for the draft the same way. `gh release view <tag>` lists it with the other assets; re-run the job, or `gh workflow run trajectory.yml -f tag=<tag>`. Before tagging, run `make trajectory` once at a terminal, so the script can ask about any commit whose time zone is not its author's that day and record the answer in `reports/trajectory/timezones.toml`; commit that file before tagging (with the release commit), since the release job reads it from the tag

## Afterwards

- **After pushing, run `make sweep`.** A just-published version makes the baseline `cargo semver-checks` cached useless, so the gate trees (19GB and 6.5GB at 0.19.3) are provably disposable at exactly that moment. It leaves `target/debug` alone and costs nothing — the next build is still incremental. See DEVELOPMENT.md, "The release gates fill target/, not day-to-day builds", for when *not* to run it
- **Then check what `target/` holds: `du -sh target/*` and `df -h .`, and say what could be freed.** `target/debug` grows without bound between releases, since cargo never deletes the old copies a build with other flags leaves behind (clippy, `--all-features`, tests, a toolchain update), and `make sweep` does not touch it. On 2026-11-13 it held 160 GB (96 GB of it `incremental/`) two days after v0.28.1's sweep; `cargo clean --workspace` freed 163 GiB and left 11 GB of dependencies. Run that when `target/debug` is tens of GB
